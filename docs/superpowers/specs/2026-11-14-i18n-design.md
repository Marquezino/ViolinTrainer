# Internationalization: English and Brazilian Portuguese

Beads issue: ViolinTrainer-3l2. Follow-up: ViolinTrainer-aim (Italian).

## Intent

The app is written in English only. It should also be fully usable in Brazilian Portuguese, with a way to switch language, and adding a third language (Italian is next) should cost little more than translating one file.

This comes before plan 2 (profiles, storage, editor, learning path, leaderboard) on purpose: plan 2 adds several screens, and their text should go into the message files from the start instead of being moved out of the code later.

## Goals

- Every user-facing text in the app exists in English (`en`) and Brazilian Portuguese (`pt-BR`).
- The language is chosen automatically from the browser on first visit and can be changed by hand; the choice is remembered.
- Note names follow the language: letter names (C D E) in English, solfège (Dó Ré Mi) in Portuguese.
- A missing or extra translation is a build error, not something noticed on screen.
- Adding a language means adding one file and one entry in a list.

## Non-goals

- Italian itself (ViolinTrainer-aim).
- Translating the README, docs, code comments or test names.
- A note-name setting separate from the language. Users understand both letter names and solfège; a setting can be added later if wanted.
- Other octave-numbering conventions (see "Note names" below).
- Translating abcjs's own warning texts (they are shown as a detail inside a translated sentence; see "Lower layers"), and translating the text of a user's own ABC (its `T:` title is shown as written).
- Right-to-left languages.

## Anti-goals

- A translation that silently falls back to English, or shows a raw key, in a released build. (The abcjs detail text is the one deliberate exception, always wrapped in a translated sentence.)
- Any change to what is judged or how: detection, scoring and tolerances must behave exactly as before. Only the text changes.
- New runtime dependencies.

## Constraints

- No i18n library (decision below). TypeScript, React 19, Vite, as in the rest of the app.
- No storage layer exists yet; plan 2 adds profiles and settings. Until then the language choice lives in `localStorage`.
- The repository is public: no personal details of users in messages, examples or tests.

## Approaches considered

1. **No library, one TypeScript module per language (chosen).** `en.ts` defines every message; other languages must have the same shape, checked by the compiler. Messages with values are functions. Plurals and number formats use the browser's `Intl`. Zero dependencies; about 60 messages do not need more. Downside: translators edit a `.ts` file rather than JSON, which is acceptable here.
2. **i18next / react-i18next.** The common choice, with plurals, fallbacks and lazy loading, messages in JSON. Adds ~40 KB, and missing translations are only caught by extra tooling or by eye.
3. **FormatJS / react-intl with ICU messages.** Standard format for professional translators; the heaviest option and the most ceremony for an app this size.

The user picked option 1.

## Design

### Languages and how one is chosen

- Supported locales: `en` and `pt-BR`, listed in one place (`src/i18n/locales.ts` or similar) with each language's own name for the menu: "English", "Português (Brasil)".
- On startup: if `localStorage` holds a saved, still-supported locale, use it. Otherwise walk `navigator.languages`; the first entry whose primary subtag is `pt` selects `pt-BR`, the first whose primary subtag is `en` selects `en`. If nothing matches, use `en`. (With Italian, `it` maps to `it` the same way.)
- `localStorage` access is wrapped in try/catch; when it fails the app still works and just does not remember the choice.
- The choice moves into profile settings in plan 2. Keep the read/write in one small module so plan 2 replaces it in one place.
- When the language changes: update `<html lang>` and `document.title`.
- The app name is a message like any other (designer's call): "Violin Trainer" in both English and Portuguese for now, so the name can be translated later without code changes. `document.title` is set from it.

### Language menu

A `<select>` in the top corner of the exercise list (picker) screen, labelled for screen readers ("Language" / "Idioma"), options shown in their own language. It is not on the practice screen, so the language cannot change mid-exercise.

```
Violin Trainer                    [ Português (Brasil) ▾ ]
Exercícios
  [ Cordas soltas ]
  [ Corda Lá: dedos 0 a 3 ]
```

### Message modules

- `src/i18n/messages/en.ts` exports the English messages. The `Messages` type is derived from it (or declared alongside it); `pt-BR.ts` is declared as `Messages`, so a missing, extra or wrongly typed message fails `npm run typecheck`.
- Plain texts are strings; texts with values are functions taking typed arguments, e.g. `wrongNote: (note: string) => \`Isso foi ${note}. Tente de novo.\``. Plurals inside such functions use `Intl.PluralRules` where the wording needs it.
- Group messages by screen or area (picker, practice, needle, microphone, room check, summary, ABC problems, exercise titles) so files stay navigable.
- A React context provides the current locale, its messages and the note-name formatter; a `useMessages()` hook (or similar) reads them. A setter changes the locale and persists it.
- Numbers shown to the user (points, decibels, cents, character positions) go through `Intl.NumberFormat` for the current locale.

### Lower layers report facts, the UI writes the text

Today several non-UI modules produce English sentences. They change to return structured data, and the UI turns that into text:

- **ABC checker (`src/score/abc.ts`).** `errors` and `warnings` become lists of problem objects: a code plus its details, e.g. `{ code: 'tooHigh', midi, highestMidi, at }`, `{ code: 'fingerImpossible', midi, finger, at }`, `{ code: 'outsideFirstPosition', midi, at }`. Every current message becomes one code (no tune found and only one tune per exercise from `parseExercise`; single melody line, repeats, chords, grace notes, tie between different pitches, unknown pitch, below G3, too high, finger 5, finger impossible in first position, outside first position, no notes). `validateTolerances` in `src/music/pitch.ts` gets the same treatment.
- **abcjs's own syntax warnings** (today the first entries of `errors`, from `tune.warnings`) get one code, e.g. `{ code: 'abcSyntax', detail, at? }`. The UI shows a translated sentence with the abcjs English text as a detail, e.g. "O ABC tem um erro de escrita perto do caractere 42: *Unknown character ignored: ¤*" (user's decision). `detail` is the only untranslated text in the app, and it is always shown inside a translated sentence. The position is included only when abcjs provides it in structured form (its parser keeps `warningObjects` at runtime, not in its type definitions; builder to check); otherwise the sentence leaves it out. Each language has a message for every code; the type should force this (e.g. a `Record<ProblemCode, ...>` in `Messages`).
- **Engine (`src/practice/engine.ts`).** `Rejection.playedName` and `NeedleReading.playedName` become the played MIDI number; the UI formats it. The `preferFlats` information the UI needs to format it must stay reachable (it is on the exercise).
- **Microphone (`src/audio/microphone.ts`).** `MicrophoneError` already has a `kind`; the UI already maps kinds to text. The internal `message` may stay English (it is for developers, not shown).
- **Exercise title fallback.** `'Untitled'` in `abc.ts` becomes "no title" (e.g. `undefined` or empty) and the UI shows the translated fallback.

### Note names

- `noteName` in `src/music/pitch.ts` takes a notation argument: `'letter'` (C D E F G A B) or `'solfege'` (Dó Ré Mi Fá Sol Lá Si). Sharps and flats keep the ♯ ♭ symbols in both: `Lá♯4`, `Si♭3`.
- Each language's messages declare which notation it uses: `en` letter, `pt-BR` solfège (Italian will be solfège too, using the Italian spellings Do Re Mi Fa Sol La Si, so the names table is per language, not one shared solfège table).
- Octaves use international (scientific) numbering in every language: middle C is C4 / Dó4, the violin's lowest note is G3 / Sol3. Some Portuguese and French material numbers middle C as Dó3, but no single Brazilian standard was found, tuners and apps use C4, and the users do not rely on octave numbers. One numbering keeps wrong-octave feedback consistent across languages.
- Everywhere a note or string name appears uses the language's notation: wrong-note feedback, the needle ("Você está tocando Lá4"), ABC problems, and fingering labels on the score, whose string names become Sol Ré Lá Mi (`Lá 2↑`). `fingeringLabel` takes the string names it needs, or the UI composes the label.
- ABC input itself is unchanged: users still write letter names in ABC.

### Built-in exercise titles

- Each built-in exercise keeps its English `T:` line in `samples.ts` (the ABC stays valid on its own), and every language has a title for it keyed by the sample's `id`. The type should force a title per sample id in every language.
- The picker buttons and the practice screen heading show the translated title for built-in exercises and the `T:` title for the user's own ABC.
- abcjs also draws the `T:` title inside the score. Builder's call (proposed): hide the abcjs-drawn title on the practice screen (it duplicates the heading and would stay English), e.g. with CSS on the `abcjs-title` class, which `ScoreView` already enables through `add_classes`. The live preview under the ABC text box keeps it, since that is the user's own text.

### Text inventory (what must move)

At least: `App.tsx`, `ExercisePicker.tsx` (headings, button labels, aria-labels, preview label), `PracticeScreen.tsx` (microphone errors, voice-processing names, room check, noisy-room hint, audio-processing hint, feedback, summary, star aria-label, buttons), `TuningNeedle.tsx` (prompt, playing label, cents sharp/flat, "In tune", flat/sharp scale labels), `ScoreView.tsx` (fingering labels and any aria-labels), `abc.ts` and `pitch.ts` messages, the starter text in the ABC box (`T:My exercise`, translated as the default title of the starter tune), `index.html` title. The builder should grep the whole `src/` for remaining English text.

### Testing

- Unit tests: `noteName` in both notations (naturals, sharps, flats, octave boundaries); locale detection from `navigator.languages` and from saved values (including an unsupported saved value and a throwing `localStorage`); ABC checker tests assert codes and details instead of English sentences; one test per language renders every ABC problem code to a non-empty string.
- The type check is the main guard for completeness; no runtime "missing key" fallback is needed.
- End-to-end (Playwright): set `locale: 'en-US'` in `playwright.config.ts` so the existing English text selectors keep working regardless of the machine. Add one test that switches to Português via the menu, checks a few translated texts (a picker heading, a built-in title, the start prompt) and checks that the choice survives a reload. Optionally one test with `locale: 'pt-BR'` checking that Portuguese is picked automatically.
- Existing behaviour tests (judging, scoring, engine) must pass unchanged apart from the `playedName` → MIDI change.

## Left to the builder

- File and identifier names inside `src/i18n/`, the exact `Messages` typing technique, and how the context and hook are shaped.
- The Portuguese wording, written in natural Brazilian Portuguese for a beginner (often a child): short sentences, "você", encouraging tone, matching the English messages' meaning exactly. The user reads Portuguese and will review it.
- Whether to add `pt-BR`-specific plural handling anywhere it is actually needed.
- Styling of the language menu, consistent with the existing CSS.
